How validation works

Validation is selected by the change’s risk and affected workflow. The scripts prepare a trusted macOS/Xcode environment, reserve a compatible simulator, run the checks for that scope, and retain evidence. A screenshot still needs human inspection.

Start with impact

The decision is about what the change can affect, not how many lines changed. Use the narrowest scope that fully covers the affected behavior; use full validation when the impact crosses boundaries or cannot be bounded confidently.

Documentation or agent guidance only

Review changed files, links, examples, and consistency. No build or simulator run.

Manual changed-file review

Localized iOS behavior with a clear workflow

Build the app and run one or more existing UI test selectors covering that behavior. If there is no relevant test, exercise it in Simulator; add a test when it protects meaningful behavior.

./scripts/validate.sh --focused OneSetUITests/Class[/testMethod] ...

Appearance or navigation change needing visual verification

Build, launch an existing preview route, capture a screenshot, then inspect spacing, clipping, typography, colors, safe areas, and the relevant state.

./scripts/validate-ui.sh --ui-<route>

Worker-only change

Run Worker typechecking and relevant API tests from the Worker package. Install locked dependencies first when needed.

npm ci --prefix worker
npm --prefix worker run typecheck
npm --prefix worker test

Simulator or validation tooling only

Run the relevant scripts under scripts/tests, then run the affected real command. This checks tooling behavior as well as its test model.

python3 -m unittest discover -s scripts/tests -v

Shared or broad impact; uncertain boundary

Shared models/services, persistence, concurrency, auth/session logic, schema, dependencies, build config, iOS plus Worker, or unclear impact all require the full suite.

./scripts/validate.sh

Appearance and behavior can overlap. A visible behavior change uses code validation. Add UI validation when appearance, screen state, or navigation also changed. Appearance-only changes can use the UI route build without interaction tests when navigation and behavior are unchanged.

Focused and full runs share the iOS gate

The default command is full. Focused mode must include at least one valid OneSetUITests/Class[/testMethod] selector. Both modes then build and test the OneSet scheme against the same booted simulator UUID.

Argument and host gate

  • With no arguments, mode is full. Unknown arguments fail before validation work.
  • Focused mode requires at least one selector matching OneSetUITests/Class or OneSetUITests/Class/testMethod; each becomes an Xcode -only-testing: filter.
  • Common setup requires macOS, full Xcode, successful first-launch setup, an iOS Simulator SDK, Python 3, a startable compiler sandbox probe where available, and a writable artifact directory.

What the full-only checks cover

  • python3 -m unittest discover -s scripts/tests -v exercises validation-command behavior, simulator discovery/recovery, and simulator lease coordination.
  • Then Worker typecheck and API tests run via npm --prefix worker run typecheck and npm --prefix worker test.
  • Install Worker dependencies first with npm ci --prefix worker (Node 22+). validate.sh does not install them itself.

Shared Xcode stage

  • One simulator UUID is passed into both build and test destinations. Build uses ONLY_ACTIVE_ARCH=YES.
  • Test disables parallel testing and writes a fresh .xcresult bundle. Focused reuses its own derived data; full reuses a separate derived-data path keyed by simulator UUID.
  • Any nonzero command stops the script. Xcode output is tee’d to a log; sandbox-like build errors get a targeted recovery hint.

Evidence locations

  • Default root is repository .codex; override with absolute writable ONESET_ARTIFACTS_DIR.
  • Each code run uses validation/<timestamp-pid>/build.log, test.log, and tests.xcresult.
  • Incremental build data: build/validation/<simulator-UUID> or build/focused/<simulator-UUID>.

The script captures; a person judges

UI validation is a build-and-preview pipeline. A successful script run proves that the app built, installed, launched the requested route, and produced a screenshot. It does not judge the screenshot or prove accessibility behavior.

Route and screenshot controls

  • Route must match an existing --ui-* value in AppLaunchConfiguration.swift; unknown routes fail before build.
  • App ID is com.oneset.OneSet. A simulator window is opened when available; CoreSimulator works headlessly too.
  • ONESET_CONTENT_SIZE optionally sets Dynamic Type; the script restores the original setting on exit. Filename includes the requested size.
  • UI build logs go under validation/ui-<timestamp-pid>/build.log; derived data is separate under build/ui/<run-name>. Screenshots go under screenshots/ inside the artifact root.

What to inspect

  • Spacing, alignment, clipping, overlap, typography, colors, safe areas, and the intended route/state.
  • Compare with a reference design when one exists. Fix issues and rerun until visually correct.
  • A Dynamic Type screenshot does not prove VoiceOver order or Reduce Motion behavior. Exercise those interactively in Simulator when the change affects them.

One UUID, one lease, bounded recovery

The scripts coordinate access to host-wide CoreSimulator devices, including runs started from different worktrees. They preserve existing simulator data and do not restart CoreSimulator.

Discovery and boot

  • Read the app deployment target; list available iOS runtimes at or above it and try newest first.
  • Choose compatible devices for the requested family (iPhone by default); prefer booted devices and reusable OneSet Validation devices.
  • With automatic selection, try up to two existing candidates, then create compatible devices with at most two creation attempts per runtime. Wait up to 180 seconds per boot by default.
  • An explicit ONESET_SIMULATOR_UDID must be available and compatible; it never silently switches to another device.

Lease and process safety

  • Exclusive lock files live in ~/Library/Caches/OneSet/simulator-locks/, independent of checkout and artifact directory.
  • Default wait for a busy device is 900 seconds. Progress reports holder PID, command, worktree, and elapsed time.
  • The protected child inherits the lock descriptor; the lock remains held for build, tests, screenshots, and restoration. Kernel locks release when owning descriptors close, including on interruption.
  • Manual simulator use does not participate in this lock. For parallel runs, use distinct UUIDs and separate worktrees or artifact roots.

Environment overrides: DEVELOPER_DIR chooses Xcode; ONESET_SIMULATOR_FAMILY=ipad chooses iPad; ONESET_SIMULATOR_UDID pins a device; ONESET_SIMULATOR_LOCK_TIMEOUT and ONESET_SIMULATOR_BOOT_TIMEOUT tune waits; ONESET_ARTIFACTS_DIR redirects outputs; ONESET_CONTENT_SIZE sets a UI screenshot text size.

Pass means these checks passed

Code Build + tests

A successful code run means Xcode build and the selected scheme tests passed; full mode also means simulator-tooling regression tests and Worker typecheck/API tests passed. No coverage threshold is defined.

UI Screenshot ready

A successful UI run means build, install, route launch, and screenshot capture completed. A person still needs to inspect the image; automated capture does not claim visual correctness.

Scope Deliberate omissions

Focused validation skips Python simulator-tooling checks and Worker checks. UI-only validation does not run interaction tests. Documentation-only review does not compile or execute the app.

Report Required handoff

Report the chosen scope and why it fits, list checks that actually ran and outcomes, mention fixes and reruns, and call interrupted or blocked validation incomplete. Inspect the final diff for unrelated changes.

Where process changes would have the most effect

These observations follow from the current scripts and docs; they are discussion points, not behavior already implemented.

Make scope selection easier to audit

Capture the change category, chosen command, and required checks in one machine-readable run summary. Today scope rationale and final outcomes are handed off in prose.

Reduce duplicate expensive setup

Full validation runs Python and Worker checks before simulator reservation, which avoids holding a device during them. The stages are serial; independent check groups could be parallelized only with explicit artifact and failure aggregation.

Strengthen visual evidence

Screenshots are captured but not compared automatically. Stable preview data plus route-specific baselines or structured screenshot review could make visual regressions easier to detect and reproduce.

Clarify evidence boundaries

Keep a clear distinction between script pass, manual screenshot approval, and interactive VoiceOver/Reduce Motion checks. A compact run manifest could record which of these happened and which remain unverified.
